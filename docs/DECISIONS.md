# Decision log

Append-only. Any change to a frozen spec, metric, baseline, budget or scoring rule after a batch exists needs a dated entry here and a new pre-registration.

## 2026-10-26

- **D-001 Project created; selection rule adopted.** NeuroAgentBench asks whether general LLM agents with tools and scientific knowledge analyse neuroscience data as well as task-specific trained models, and how much of their performance comes from using those models as tools. The task-selection rule in `docs/TASK_SELECTION.md` (hidden or post-cutoff test labels or a possible private re-split; runnable published SOTA; at most about one GPU-day per run; added modality coverage) is adopted before any candidate is assessed. The five pilot tasks predate the rule and are reported separately. Integrity tooling is adapted from dark-gene-bench: pre-registration guard (now also requiring a clean `tasks/`, and carrying the run plan), batch ledger with one batch per pre-registration commit, data, run and truth roots outside the repository, completeness rule for final reports, and CLI backends with empty stdin and recorded commands and versions. The per-model empty working directory becomes a fresh workspace per run attempt, inside an OS sandbox.

- **D-002 Name to be reconsidered before public release (collision with NeuroAgent).** NeuroAgent (arXiv 2605.06584) is a neuroimaging agent framework with a near-identical name. Decide on the name before D8 (public release); see `docs/RELATED_WORK.md`.

- **D-003 Pilot scope and run rules (owner, before any batch).** The pilot pre-registration (`prereg/pilot-bwb.md`) plans bwb_neuropixels_wheel under C1, C2 and C3, three reps, plan seed 20261027. C5 is omitted for every model in the pilot, so the unfilled Codex native-mode command is removed. The pilot runs two model families; the open-weights model is deferred, and the pilot report must state that the open-weights requirement (D5) is not yet met. No exclusions: a run still erroring after `run.max_attempts` (3) gets an empty submission and scores every case as missing, and `run_batch.py --until-done` retries every 10 minutes until nothing is missing. Token budgets are logged only for the pilot and wall time is the hard cap; an enforced cost cap is required before the main suite. Baselines run on the same Mac as the agents; a SOTA rerun that cannot finish there within the task's wall time counts as failing rule (c) on this harness. Agent CLI commands now set their own sandbox offline (Claude Code `--settings` sandbox with an empty strict allowlist; Codex `sandbox_workspace_write.network_access=false` and `web_search="disabled"`), both CLIs are enabled, and the network probe then a dummy-task smoke batch are approved as their first invocations.

- **D-004 Agent CLIs run as a separate macOS user (owner, before any batch).** The first network probes failed closed for both CLIs: each CLI's own sandbox (`sandbox-exec`) cannot start inside the harness's `sandbox-exec` profile, because any file-deny rule in the outer profile makes the inner `sandbox_apply` fail (reproduced without an agent). Models with `isolation: agent_user` therefore run without the harness sandbox, as the user `nabagent`, which a deny ACL keeps out of the harness user's home; the runner checks before every run that it cannot enter the home, repository or data, runs and truth roots. The CLI's own sandbox keeps agent commands offline, verified by the network probe, whose control now runs as the agent user. Workspaces are staged under `/Users/Shared/nab-agent/workspaces`, opened to the agent user by an ACL for the run, then closed and moved to `runs_root`. Agents use a pinned copy of the Claude CLI and a shared Python environment with the specs' generic tools (`scripts/setup_agent_user.sh`). Each run gets an empty HOME and TMPDIR (`sandbox.agent_home`) seeded only with the model's `keep` sign-in files and a `.zprofile` that restores `sandbox.agent_path` (macOS login shells, which Codex runs commands in, otherwise put `/usr/bin` and its Xcode `python3` stub first), which are saved back afterwards to a store the agent user cannot read; then every process of the agent user is killed and everything it owns in `/private/tmp`, `/Users/Shared` and its own temp and cache directories, and any file it created in its real home outside `Library`, is deleted. Sign-in goes through the same path (`scripts/agent_login.py`). Claude keeps its sign-in in the macOS keychain, so the agent user gets a keychain (`nabench`, empty password, file permissions as the protection, like Codex's `auth.json`) that each run's home is pointed at; the agent user creates that home itself, since macOS will not set a default keychain under a HOME the user does not own. Chosen over a harness-only sandbox with an API proxy (agent code could call the model API directly, outside token logging) and a Linux VM. The scripted stand-in still runs under `sandbox-exec`.

- **D-018 GPU SOTA rerun: 4 h, seed rule, precision (owner; deviation after batch b-20261028-044630-f61b was generated; settles the question left open in D-010).**
  - **Limit:** the rerun gets 4 h of wall time, counted from the start of the job script and enforced at the end of every epoch.
  - **Seeds:** seed 1 runs on every session first. Seeds 2-5 run if five times seed 1's time fits in 4 h, and they are kept only if they all finish in time; otherwise the result is seed 1 alone. If seed 1 does not finish every session, there is no SOTA.
  - **Precision:** training uses bf16 autocast, as the benchmark did, if the GPU supports bf16; otherwise fp32.
  - **Provenance:** the job writes the GPU model, precision, seeds run and fit time into `provenance.json`, which `MANIFEST.sha256` covers. The manifest stays a plain checksum list because the batch's `sota_baseline` parses it. `scripts/sota_gpu.py import` refuses any result that breaks these rules.
  - **Where the code lives:** `scripts/sota_gpu_job.py` and `src/nabench/tasks/bwb_sota_gpu.py`. `bwb_neuropixels_wheel.py` is unchanged, because the running batch imports it; bf16 is applied by the job script around the model's forward pass. The job no longer resumes; each run is one attempt of at most 4 h.
  - **Not settled:** a seed-1-only result cannot be used by batch b-20261028-044630-f61b. That batch's `sota_baseline` check and its reference rows `sota_seed1`..`sota_seed5` expect five seeds, so the import refuses it, and the report could never become final. If that case arises, it needs an owner decision and a code change.

- **D-019 GPU SOTA seeds in parallel; no partial-seed fallback (owner, before any GPU run; supersedes D-018's seed rule and settles its open point).**
  - **Parallel seeds:** the 5 SOTA seeds may run in parallel, on separate GPUs or as concurrent processes on one GPU.
  - **Limit:** the 4 h wall-time limit covers the whole job, from the first seed starting to the last seed finishing.
  - **No fallback:** if a single seed cannot finish all 29 sessions within 4 h, the job stops, nothing is imported, and BWB is recorded as failing rule (c) on that hardware. There is no seed-1-only result.
  - **Implementation, GPU side only:**
    - `run_sota.py --seeds S...` runs a subset and writes a part with each seed's GPU, precision, start and end.
    - Each process stops at the first epoch end past 4 h from its own start.
    - `run_sota.py --merge` combines parts into the standard 5-seed result. It records each seed's GPU, start and end, and the job's overall wall time. It refuses parts from another export, missing or repeated seeds, or a job over 4 h.
    - `scripts/sota_gpu.py import` refuses a result whose overall wall time, recomputed from the seeds' times, exceeds 4 h. Across machines this relies on their clocks agreeing.
    - `--smoke` projects seconds per session per seed from 42 epochs of one session.
  - **Batch code unchanged:** no code the running batch imports changed.

- **D-021 Claude token counts from the cumulative `modelUsage` (owner, 2026-10-28; after batch b-20261028-044630-f61b was generated).**
  - **Problem:** `parse_usage` took the Claude CLI's final `usage` object. When a run is resumed by a background-task notification, that object covers only the last turn. In b-20261028-044630-f61b, 4 of the 6 opus runs were undercounted: C2 opus was recorded as 292,350 in / 2,364 out over 3 runs, against 5,492,650 / 47,160 cumulative.
  - **Fix:** with `usage: last`, a final object that carries `modelUsage` now gives its totals summed over models (input, cache read, cache creation, output). The other CLIs and the scripted stand-in are unchanged.
  - **Sol:** its counts cannot be checked against session logs, because none exist: Codex runs with `--ephemeral`, and the agent home is emptied after every run. Each Sol run's output has exactly one `turn.completed` event, which `usage: sum` takes as is.
  - **This batch:** `runs.jsonl` stays as recorded. Every run's counts, recomputed from its saved CLI output with the new parser, are in `investigation/3_tokens_recomputed.jsonl`. No run exceeded the 3 M token budget; the largest used 2.72 M in + out.

- **D-022 Exploratory GPU variant: POYO+ refit on train+val (owner, 2026-10-28, before any GPU run; not the SOTA baseline).**
  - **What:** `run_sota.py --trainval [--seeds S...]` first runs the frozen fit for each session and seed: train trials, with the best epoch picked on val. It then finetunes POYO+ afresh from the checkpoint on train+val for that count of epochs (best epoch + 1), on the same schedule: OneCycleLR over 300 epochs with steps per epoch from train+val, and the backbone frozen until epoch 40. The final weights predict test. It follows D-018's precision rule and has no time limit. It writes `seeds/` (the train-only fits), `trainval/` and each fit's epoch count in `part.json`.
  - **Never SOTA:** `--merge` refuses variant parts, so the variant can never become or be imported as the SOTA result. Any scoring of it is exploratory, done on the harness.
  - **Frozen job unchanged:** without `--trainval`, `run_sota.py` runs the D-019 job as before, and `bwb_neuropixels_wheel.py` is unchanged. The variant reuses `poyo_finetune` unchanged. It puts the test trials in the validation slot and replaces the per-epoch R² with a stand-in (`bwb_sota_gpu.stop_after`) that stops after the chosen epoch count.
  - **Export:** `~/sota-export` is left as is (`MANIFEST.sha256` SHA-256 `d6dcfb0a…ab9f6b`). The variant needs the new `run_sota.py` and `code/nabench/tasks/bwb_sota_gpu.py`, so a second export, `~/sota-export-2` (`0be52dac…076d37`), differs in those two files only. Its default path is the same frozen job.
  - **Projected extra GPU time:** about 2.1 to 2.2 times the frozen job's.
    - Repeating the train-only fits (needed to pick the epoch count) costs 1.0 times the frozen job.
    - The refits cost 1.07 to 1.15 times the frozen job:
      - Train+val holds 1.445 times the train trials (11,266 vs 7,795 over the 29 sessions).
      - A refit runs about 74 epochs (best epoch + 1, if the published runs' 93-epoch average ended on patience 20), against 93 for a fit.
      - The range covers backbone-frozen epochs costing 0.5 to 1 times a full epoch.
    - Not counted: a forward pass over the test trials each refit epoch, in place of the val pass.
    - `--smoke` on the target GPU gives the per-session time these multiply.
